## 1. The problem statement (as issued)

**Problem Statement ID:** 26156
**Title:** Universal Log Pre-processing Framework

### Background
Modern enterprises generate massive volumes of logs from a wide range of sources, including network devices, servers, operating systems, applications, databases, cloud services, containers, endpoint security tools, identity and access management systems, IoT devices, and other hardware and software platforms. These logs are produced in diverse formats such as Syslog, JSON, XML, CSV, CEF, LEEF, proprietary vendor formats, and application-specific schemas.

The diversity of log structures creates significant challenges in centralized monitoring, security operations, compliance reporting, incident investigation, and threat analytics. Security teams often spend substantial effort developing source-specific parsers and normalization rules before the data can be effectively utilized by SIEM, data lake, or machine learning platforms.

As organizations adopt hybrid, multi-cloud, and AI-driven environments, the need for a universal and extensible log standard that can accommodate both current and future data sources has become increasingly critical.

### Detailed description
Design and develop a Universal Log Pre-processing Framework (ULPF) capable of ingesting, parsing, normalizing, and standardizing logs and events generated by any hardware or software system.

The framework should support diverse event sources while preserving the original event data for forensic and compliance purposes. It should transform heterogeneous logs into a unified schema that enables consistent analytics, correlation, visualization, threat hunting, anomaly detection, and machine learning applications.

The framework must be scalable, extensible, vendor-agnostic, and suitable for deployment in Big Data environments handling billions of events per day.

### Expected solutions
The solution should cover a universal event schema and processing framework that enables:

- **a)** Preserve complete raw event data without information loss.
- **b)** Extract and parse source-specific attributes.
- **c)** Normalize fields into a common event taxonomy.
- **d)** Maintain traceability between normalized and original events.
- **e)** Plug-and-play onboarding of new log sources.
- **f)** Unified visibility across enterprise environments.
- **g)** Efficient SIEM and Data Lake integration.
- **h)** AI/ML-ready security and operational analytics.
- **i)** Reduced parser development effort.
- **j)** The solution shall be deployable in an air-gapped network.
- **k)** Solution may be packaged in a container for making it platform independent.

### Current scope
Build a framework that converts any perimeter network device-generated log or event, regardless of source, format, vendor, or technology, into a standardized, lossless, analytics-ready representation for next-generation SIEM and cybersecurity platforms.

## 2. Understanding the problem

### 2.1 The problem in plain terms
A Security Operations Centre (SOC) receives logs from many perimeter devices: firewalls, routers, IDS/IPS sensors, VPN concentrators, web proxies and web application firewalls (WAFs). Each vendor, and often each firmware version, writes logs in its own layout. Before the SOC can search, correlate or run machine learning on these logs, engineers must write a parser for each source that extracts fields and maps them to common names. This parser work is slow, it never ends (new devices, new firmware), and it is fragile: a small format change can make a parser silently extract wrong values or stop matching.

At the same time, the original log must be kept exactly as received, because investigators, auditors and courts rely on original evidence. Today this is usually done by storing a raw copy next to the parsed copy, which doubles storage. The link between the two is typically only an event ID, so no one can show precisely which bytes of the original produced which normalized field.

### 2.2 Who is affected
| Stakeholder | Pain today |
|---|---|
| Detection / SIEM engineers | Writing and maintaining one parser per source and version |
| SOC analysts | Inconsistent field names across vendors make correlation hard; missed detections |
| Forensic investigators | Need the untouched original and proof that it was not altered |
| Compliance teams | Must retain logs for long periods; storage cost grows with volume |
| Data scientists | Need clean, typed, consistent features to build models |

### 2.3 What each requirement really asks
| Req | Literal text | Engineering interpretation |
|---|---|---|
| a | Preserve raw without loss | Every byte received must be recoverable exactly, including for events that could not be parsed |
| b | Extract source attributes | Vendor-specific fields must be pulled out, not only common ones |
| c | Normalize to a taxonomy | A single, documented schema with fixed field names and types |
| d | Traceability | From any normalized field, one must be able to get back to the original event (and ideally to the exact bytes) |
| e | Plug-and-play onboarding | Adding a source must not require changing or redeploying core code |
| f | Unified visibility | One place to see all sources in the same shape |
| g | SIEM and data lake integration | Standard outputs that existing platforms can consume |
| h | AI/ML ready | Typed, consistent, columnar data suitable for feature extraction |
| i | Reduced parser effort | Measurably less human work per new source |
| j | Air-gapped | No internet access at install or run time |
| k | Containerized | Runs the same on any host with a container runtime |

### 2.4 Implicit constraints hidden in the wording
- **Scope is narrowed.** The current scope is perimeter network devices only. The framework must be extensible to anything, but the prototype is judged on perimeter devices.
- **Scale is a real requirement.** "Billions of events per day" translates to sustained throughput:
  - 1,000,000,000 events / 86,400 seconds is about **11,574 events per second** on average.
  - Real traffic is bursty; planning for a 3x peak gives about **35,000 events per second** per billion events per day.
  - Storage matters as much as throughput. At an assumed 300 bytes per event, 1 billion events is about 300 GB of raw text per day before compression.
- **Air-gapped rules out cloud services and cloud AI APIs** at every stage, including installation.
- **Lossless is a strong word.** Keeping "most" of the data, or keeping raw only for successfully parsed events, does not meet requirement (a).

## 3. Solution overview

### 3.1 One-line description
Aletheia (Greek for "truth", literally "un-concealment": nothing hidden, nothing lost) learns a **template** for each log format, stores every event as that template plus the variable values extracted from it, and uses this single representation for three purposes at once: **normalization, compression and exact reconstruction of the original**. Every event's reconstruction is verified by a SHA-256 hash, and hashes are sealed into a tamper-evident Merkle chain.

### 3.2 The core insight, with a real example
A Cisco ASA firewall log line:

```
<166>Sep 19 14:31:02 fw01 %ASA-6-302013: Built outbound TCP connection 1234 for outside:203.0.113.5/443 (203.0.113.5/443) to inside:10.0.0.5/52144 (198.51.100.7/52144)
```

Aletheia splits it into **literal text that is the same for every event of this type** and **variable values that change per event**:

```
template (stored once):
  "<" PRI ">" TS " " HOST " %ASA-6-302013: Built " DIR " TCP connection " CONN_ID
  " for " IF_A ":" IP_A "/" PORT_A " (" MIP_A "/" MPORT_A ") to " IF_B ":" IP_B "/" PORT_B
  " (" MIP_B "/" MPORT_B ")"

variables (stored per event):
  ["166", "Sep 19 14:31:02", "fw01", "outbound", "1234", "outside", "203.0.113.5", "443",
   "203.0.113.5", "443", "inside", "10.0.0.5", "52144", "198.51.100.7", "52144"]
```

From this one parse:
1. **Normalization:** each variable slot has a meaning, so `IP_B` maps to the OCSF field `src_endpoint.ip`, and so on.
2. **Compression:** the long literal text is stored once per template, not once per event. Only the short variables are stored per event, in typed columns that compress very well.
3. **Reconstruction:** concatenating template literals and variables in order gives back the original line exactly. The SHA-256 of the reconstruction is compared with the SHA-256 computed when the event arrived. If they match, the event is provably lossless. If they ever differ, the original bytes are stored verbatim instead, so nothing is lost even when something goes wrong.

### 3.3 The five pillars
| Pillar | What it means | Mechanism |
|---|---|---|
| **Standard** | One universal schema | OCSF (Open Cybersecurity Schema Framework) output, an `unmapped` object for leftovers, and an explicit `parse_status` |
| **Proof** | Losslessness and integrity are verifiable | Byte-exact reconstruction, per-event SHA-256, per-minute Merkle roots chained over time, byte-level field lineage |
| **Economy** | Keeping everything costs less, not more | Template dictionary plus variable columns as the storage format |
| **Safety** | Format changes and parser changes cannot silently corrupt data | Drift detection with quarantine, a reconstruction gate for any proposed parser, replay "blast radius" diff before approving a parser change |
| **Reach** | Works with what organizations already run | Sinks to ClickHouse, Parquet data lake, Grafana Loki, Kafka, Splunk HEC, and CEF re-emit to any SIEM |

### 3.4 Design principles
1. **Raw first.** Raw bytes are durably committed and hashed before any parsing.
2. **Never drop.** An event that cannot be parsed is still stored (verbatim) and counted.
3. **Deterministic hot path.** Per-event processing uses only compiled, deterministic code. No machine learning model or LLM ever touches live events.
4. **Stored values are exact substrings.** Variables are stored exactly as they appeared. Typed, normalized values are derived from them, never replacing them.
5. **Every output is attributable.** Each normalized event records which parser pack and version produced it and the hash of its original.
6. **Standards over invention.** OCSF for the schema, syslog/CEF/LEEF standards for inputs, Kafka protocol for transport.
7. **Offline by construction.** Nothing requires network access outside the deployment.

### 3.5 What Aletheia is not
- It is not a SIEM. It prepares data for SIEMs, data lakes and ML.
- It is not an "AI log parser". AI is an optional helper during onboarding and its suggestions are accepted only if they pass a byte-exact reconstruction test.
- It is not a new schema. It uses OCSF and adds a small provenance block.

## 4. Core concepts and vocabulary

| Term | Definition |
|---|---|
| **Raw event** | The exact bytes of one log message as delivered by the transport, after transport framing is removed (newline or octet-count framing). Includes any syslog header. |
| **Source** | A configured log emitter, identified by `source_id`, resolved from the sender's IP address and listener port. Carries vendor, product, device type and timezone. |
| **Envelope** | The transport or wrapper structure around the message: syslog RFC 3164 header, RFC 5424 header, CEF header, LEEF header. |
| **Body** | The message content inside the envelope. |
| **Template** | An ordered list of tokens. Each token is either a **literal** (exact bytes that must match) or a **slot** (a variable with a type). A template describes one message family. |
| **Slot** | A named, typed variable position in a template (for example `src_ip: ip`). |
| **Variables (vars)** | The exact substrings captured by the slots for one event. |
| **Parser pack** | A versioned YAML file that defines one or more templates, how to find them, and how their slots map to OCSF fields. |
| **Reconstruction** | Rebuilding the raw event by concatenating literals and variables in template order. |
| **Verification** | Checking `SHA-256(reconstruction) == SHA-256(raw)` computed at arrival. |
| **Storage mode** | `template` (stored as template id plus vars) or `verbatim` (raw bytes stored as-is). |
| **Parse status** | `full` (all slots typed and mapped), `partial` (matched, but some slots failed type validation or were unmapped), `raw_only` (no template matched). |
| **Lineage** | The byte offsets `[start, end)` of each variable in the raw event, computed from the template and vars. |
| **Merkle batch** | All events of one source, one bus partition, and one ingest minute. Its event hashes form a Merkle tree whose root seals the batch. |
| **Merkle chain** | Each batch root is hashed together with the previous chained root, so altering any past batch breaks every later link. |
| **Drift** | A source starts emitting messages that no known template matches, usually after a firmware or configuration change. |
| **Quarantine** | Where unmatched events are referenced for onboarding. They are also stored verbatim immediately, so quarantine never means "not stored". |
| **Reconstruction gate** | The rule that a proposed template is rejected unless it reconstructs 100% of its sample lines byte-exactly. |
| **Replay diff** | Re-running recent historical events through a proposed parser version and comparing its output with the current version's output. |
| **OCSF** | Open Cybersecurity Schema Framework, an open, vendor-neutral schema for security events, organized into categories and classes. |

### 5.3 Bus topics
| Topic | Key | Content | Retention purpose |
|---|---|---|---|
| `raw` | `source_id` | Exact raw bytes + headers | Durable buffer; raw is safe here before any parsing; supports reprocessing after outages |
| `quarantine` | `source_id` | References (event_uid, source_id) plus raw bytes of unmatched events | Input for the Onboarding Studio |

## 6. Component specifications

Each component is described by purpose, input, output, behaviour, failure handling and design rationale.

### 6.1 [1] Collectors (Vector)
- **Purpose:** Receive logs from devices without altering their content.
- **Input:** Syslog over UDP, TCP and TLS (RFC 5425), and file tailing for devices that write local files.
- **Configuration essentials:**
  - Use Vector's `socket` source with `decoding.codec = "bytes"` so the message is not parsed or modified.
  - Framing: `newline_delimited` for most TCP senders, `octet_counting` for RFC 6587 octet-counted TCP syslog. UDP datagrams are one message each.
  - Add metadata: receive timestamp (ms), peer address, listener port.
- **Output:** Kafka-protocol messages to Redpanda topic `raw`. The **message value is the exact raw bytes**; metadata travels in Kafka headers, never inside the value.
- **Why metadata in headers:** The hashed raw event must be exactly what the device sent. Adding a JSON wrapper around it would change the bytes being preserved.
- **Failure handling:** Vector uses disk buffers so that a short Redpanda outage does not lose data. UDP is inherently lossy on the network; TCP or TLS is recommended for sources that support it, and this is stated as a deployment recommendation.
- **Why Vector:** Mature, high-performance (written in Rust), supports all needed transports and framing, and avoids writing and securing a custom network listener.

### 6.2 [2] Ingest bus (Redpanda)
- **Purpose:** Durable, replicated, replayable buffer between collection and processing.
- **Partitioning:** Keyed by `source_id`, which keeps each source's events in order within a partition. Very high-volume sources can be salted (`source_id#0..n`) to spread across partitions; Merkle batches are then per `(source_id, partition, minute)`, so ordering requirements still hold within each batch.
- **Retention:** Configured to cover the maximum expected processing outage plus reprocessing needs (for example 7 days). This is the "raw first" guarantee: raw bytes are replicated to disk before any parsing starts.
- **Why Redpanda:** Kafka-compatible (all Kafka clients and tools work), single binary without ZooKeeper, simpler to operate in an air-gapped environment.

### 6.3 [3] Evidence stamp
- **Purpose:** Give every event a stable identity and an integrity fingerprint before anything else happens.
- **event_uid:** A ULID (128 bits: 48-bit millisecond timestamp plus 80 bits of entropy, lexicographically sortable). Aletheia makes it **deterministic**:
  - timestamp part = receive time from the collector header
  - entropy part = first 80 bits of `SHA-256(topic || partition || offset)`
  Because the bus offset of a message never changes, redelivering the same message after a crash produces the same `event_uid`. This makes all downstream writes idempotent.
- **raw_sha256:** `SHA-256(raw bytes)` exactly as stored in the bus value.
- **Merkle leaf:** The pair `(event_uid, raw_sha256)` is registered with its batch key `(source_id, partition, ingest_minute)`. The ingest minute comes from the receive time, so batch membership is deterministic.
- **Output:** An in-memory event record passed to the next stage.

### 6.4 [4] Envelope decoder
- **Purpose:** Identify and split the wrapper so the matcher can work on a smaller, predictable body.
- **Detects:**
  - RFC 5424: starts with `<PRI>` followed by a version digit `1` and a space.
  - RFC 3164 (BSD syslog): `<PRI>` followed by a `Mmm dd hh:mm:ss` timestamp (note: single-digit days are space-padded, `Sep  9`).
  - Devices that omit hostname or use nonstandard timestamps are covered by additional envelope templates.
  - CEF: body begins with `CEF:` followed by a version.
  - LEEF: body begins with `LEEF:` followed by a version.
  - Body type hints: begins with `{` (JSON candidate), contains repeated `key=value` (KV candidate), comma counts (CSV candidate).
- **Output:** Envelope type, envelope slot values (PRI, timestamp, host, tag), body byte range, and a **discriminator** used by the matcher (for example `%ASA-6-302013`, the CEF vendor/product/signature id, the syslog tag `filterlog`, the FortiGate `logid`).
- **Note:** The envelope itself is expressed as templates, so reconstruction covers the entire raw event, header included.

### 6.5 [5] Template matcher
- **Purpose:** Find the template that describes this event.
- **Index:** A hash map from `(source_id or vendor/product, envelope type, discriminator)` to a short, ordered list of candidate templates. This reduces matching to a few regex attempts per event instead of trying every template.
- **Match:** Each template is compiled to a **fully anchored** RE2 regular expression (`^...$`). The first candidate that matches wins. Candidate order is deterministic (most specific first, defined in the pack).
- **On miss:**
  - The event is stored immediately with `storage_mode = verbatim` and `parse_status = raw_only`. Best-effort envelope fields (time, host) are still populated.
  - A reference plus the raw bytes are published to the `quarantine` topic.
  - Nothing is dropped.
- **Why RE2:** RE2 (Go's `regexp`) guarantees linear-time matching. Backtracking engines (used by grok in many tools) can hit catastrophic backtracking on adversarial or unexpected input, which stalls pipelines and is a denial-of-service risk.

### 6.6 [6] Extract, reconstruct, verify
- **Extract:** Capture groups become the variables, stored as **exact byte substrings**.
- **Reconstruct:** Concatenate literals and variables in template order.
- **Verify:** `SHA-256(reconstruction) == raw_sha256`.
  - Because the regex is fully anchored and every byte is covered by either a literal or a capture group, a successful match reconstructs exactly by construction. Verification therefore guards the **whole path**: encoding handling, engine bugs, storage round-trips and later reads. It is an end-to-end check, not just a parsing check.
  - On mismatch (which should never happen and is treated as an engine defect): store verbatim, increment a metric, emit to `dlq` with context.
- **Lineage spans:** Byte offsets of each variable are computed by walking the template: offset starts at 0, each literal advances by its length, each variable records `[offset, offset + len)` then advances. Spans are **not stored**; they are recomputed on demand from template and vars.

### 6.7 [7] OCSF normalizer
- **Purpose:** Turn variables into typed, standard OCSF fields.
- **Steps:**
  1. **Type validation and coercion** per slot type (IP parses as IPv4/IPv6; port is an integer 0 to 65535; timestamps parse; enums are in the allowed set).
  2. **Class and activity selection** from the pack (for example Network Activity, activity "Open").
  3. **Field mapping** from slot to OCSF path, with optional transforms and conditions (Section 7.3).
  4. **Constants** from the source registry (vendor, product, device type).
  5. **Unmapped**: slots with no mapping go into `unmapped` under their slot name, so vendor-specific attributes are always kept (requirement b).
  6. **Status:** `full` if every slot validated and every mapped field was set; `partial` if any validation failed (the raw variable is still stored, so nothing is lost).
- **Time handling:**
  - RFC 3164 timestamps have no year and no timezone. Year is inferred from receive time (with December/January rollover handling: if the parsed month is December and the receive month is January, use the previous year). Timezone comes from the source registry.
  - The original timestamp string is kept in `metadata.original_time`.
  - If no event time can be parsed, the receive time is used and the fact is recorded.
- **Output:** One normalized record written to ClickHouse and published to `normalized`.

### 6.8 [8] Storage and sinks
Covered in Sections 7.5 and 11. ClickHouse is the system of record. Other sinks receive copies.

### 6.9 Merkle sealer
- **Purpose:** Make stored evidence tamper-evident.
- **Batch closing:** A batch `(source_id, partition, minute)` closes after the minute ends plus a grace window (for example 2 minutes) to absorb in-flight events. Events always belong to the batch of their **ingest** minute, so late events never reopen old batches.
- **Root:** Leaves are `raw_sha256` values ordered by `event_uid`. The tree is a standard binary Merkle tree (an odd node is paired with itself).
- **Chain:** `chained_root_n = SHA-256(chained_root_(n-1) || root_n || source_id || partition || minute)`.
- **Storage:** Roots and chained roots in PostgreSQL. Optionally, a daily anchor (the latest chained root per source) is signed with an Ed25519 key held by the organization and written to MinIO or printed for off-system custody.
- **Why chaining matters:** A hash stored next to its data can be recomputed by whoever alters the data. Chaining plus off-system anchors means altering one event requires rewriting every later root and forging the anchor signature.

### 6.10 Parser registry
- Parser packs are YAML files in a Git repository with test samples and expected outputs.
- PostgreSQL holds the pack index: id, version, status (`proposed`, `approved`, `retired`), author, approver, timestamps and the hash of the replay diff report that was reviewed before approval.
- On approval, the registry publishes `{pack_id, version, checksum}` on the `control` topic.
- **Hot reload in workers:** Workers fetch the new pack, compile all templates into a new matcher index in the background, and swap an atomic pointer. In-flight events finish with the old index. No restart, no downtime.
- Old versions are never deleted, so any event can be re-examined with the exact version that produced it.

### 6.11 Onboarding Studio
Detailed in Sections 8.6 to 8.12. The optional AI assistant it can call is specified in Section 8.12. In short: it turns quarantined events into proposed parser packs, tests them rigorously, and presents them for human approval.

### 6.12 Replay engine
- The same Go engine binary run in batch mode (`aletheia replay`).
- Input: a source and a time range or event count, plus two pack versions.
- For each event it reconstructs the raw bytes from storage, runs both versions, and diffs the normalized outputs field by field.
- Also used for **reprocessing**: re-normalizing historical events with a new pack version (Section 12.5).

### 6.13 Verify tool
- `aletheia verify --source fw01 --from T1 --to T2`
- For each event in range: reconstruct (or read verbatim), hash, compare with stored `raw_sha256`. For each batch: recompute the Merkle root and the chain, compare with stored roots and, if present, the signed anchor.
- Output: pass/fail per batch, and the exact events and batches that fail.

## 7. Data model and contracts

### 7.1 Raw message on the bus
| Part | Content |
|---|---|
| Value | Exact raw bytes (no wrapper) |
| Header `pr_recv_ms` | Receive time, epoch milliseconds |
| Header `pr_peer` | Sender address and port |
| Header `pr_listener` | Listener protocol and port |
| Key | `source_id` (resolved by collector from peer/listener via a static mapping), or `unknown:<peer_ip>` |

### 7.2 Template token model
A template is a list of tokens:

```yaml
- lit: "<"                 # literal bytes, matched exactly
- slot: pri                # variable
  type: int
- lit: ">"
- slot: ts
  type: syslog3164_ts
- lit: " "
- slot: host
  type: hostname
- lit: " %ASA-6-302013: Built "
- slot: direction
  type: enum
  values: [inbound, outbound]
```

**Slot types and their default RE2 sub-patterns**
| Type | Pattern (simplified) | Validation |
|---|---|---|
| `int` | `\d+` | parses as integer |
| `port` | `\d{1,5}` | 0 to 65535 |
| `ipv4` | dotted quad | each octet 0 to 255 |
| `ipv6` | hex groups with `:` (and `::`) | parses as IPv6 |
| `ip` | ipv4 or ipv6 | parses as IP |
| `mac` | six hex pairs with `:` or `-` | parses as MAC |
| `hostname` | `[A-Za-z0-9._-]+` | length limit |
| `syslog3164_ts` | `[A-Z][a-z]{2} [ \d]\d \d{2}:\d{2}:\d{2}` | valid date/time |
| `iso8601_ts` | ISO 8601 with optional fraction and offset | parses |
| `epoch_ts` | `\d{9,10}(\.\d+)?` | plausible range |
| `enum` | alternation of allowed values | in set |
| `word` | `\S+` | none |
| `quoted` | `"(?:[^"\\]|\\.)*"` | none |
| `text` | `.*?` (lazy), allowed only when followed by a literal or at the end | none |
| `custom` | pattern given in the pack | pack-defined |

**Rule:** Templates compile to `^` + tokens + `$`. Literals are escaped with `regexp.QuoteMeta`. Every slot is a capture group.

### 7.3 Parser pack specification
```yaml
pack: cisco_asa
version: 4
applies_to:
  vendor: Cisco
  product: ASA
envelopes: [rfc3164_std, rfc3164_nohost]      # envelope templates this pack's bodies can follow

templates:
  - id: asa_302013
    discriminator: "%ASA-6-302013"
    body:
      - lit: "%ASA-6-302013: Built "
      - {slot: direction, type: enum, values: [inbound, outbound]}
      - lit: " TCP connection "
      - {slot: conn_id, type: int}
      - lit: " for "
      - {slot: if_a, type: word}
      - lit: ":"
      - {slot: ip_a, type: ip}
      - lit: "/"
      - {slot: port_a, type: port}
      - lit: " ("
      - {slot: mip_a, type: ip}
      - lit: "/"
      - {slot: mport_a, type: port}
      - lit: ") to "
      - {slot: if_b, type: word}
      - lit: ":"
      - {slot: ip_b, type: ip}
      - lit: "/"
      - {slot: port_b, type: port}
      - lit: " ("
      - {slot: mip_b, type: ip}
      - lit: "/"
      - {slot: mport_b, type: port}
      - lit: ")"

    ocsf:
      class_uid: 4001               # Network Activity
      activity_id: 1                # Open
      constants:
        connection_info.protocol_name: tcp

        # and the initiator on inbound connections, so mapping depends on direction.
        - when: {direction: outbound}

            ip_b: src_endpoint.ip
            port_b: src_endpoint.port

            port_a: dst_endpoint.port
```

**Pack fields explained**
| Field | Meaning |
|---|---|
| `pack`, `version` | Identity; version increments on every approved change |
| `applies_to` | Which sources may use this pack |
| `envelopes` | Allowed envelope templates |
| `templates[].discriminator` | Fast index key; must appear in the body |
| `templates[].body` | Token list |
| `ocsf.class_uid`, `activity_id` | Target class and activity |
| `constants` | Fixed values set on every event of this template |

| `conditional` | Mappings applied only when slot values match the `when` clause |
| `unmapped_keep` | Slots deliberately kept in `unmapped` |
| `tests` | Golden samples and expected normalized outputs; run in CI and in the gate |

## 8. Algorithms in detail

### 8.1 Worker loop (per message)
```text
for message in consume(raw):
    uid   = deterministic_ulid(message.recv_ms, message.topic, message.partition, message.offset)
    h     = sha256(message.value)
    batch = (message.source_id, message.partition, minute(message.recv_ms))
    merkle.add_leaf(batch, uid, h)

    env = envelope.decode(message.value)
    t, caps = matcher.match(message.source_id, env)

    if t is None:
        rec = verbatim_record(uid, h, env, status="raw_only")
        publish(quarantine, ref(uid, message))
    else:
        vars = caps                                   # exact substrings
        if sha256(reconstruct(t, vars)) != h:         # end-to-end guard
            rec = verbatim_record(uid, h, env, status="raw_only")
            publish(dlq, error("reconstruct_mismatch", uid, t))
        else:
            rec = normalize(t, vars, source_registry[message.source_id])
            rec.storage_mode = "template"

    batcher.add(rec)                                  # ClickHouse batch insert
    publish(normalized, to_ocsf_json(rec))

on batcher.flush_success:
    commit_offsets()                                  # at-least-once, idempotent by uid
```

### 8.2 Deterministic ULID
```text
ts_ms   = recv_ms                                      (48 bits)
entropy = first_80_bits(sha256(topic || partition || offset))
uid     = crockford_base32(ts_ms || entropy)           (26 chars)
```
Same message, same offset, same uid, on any redelivery.

### 8.3 Template compilation
```text
regex = "^"
for token in envelope_tokens + body_tokens:
    if token.lit: regex += quote_meta(token.lit)
    else:         regex += "(" + pattern_for(token.type, token) + ")"
regex += "$"
compile with RE2
```
Ambiguity: when two adjacent slots could split a substring in more than one way, reconstruction is still exact (every byte is captured somewhere), but meaning could shift. Packs avoid this by always separating slots with a literal; the Studio refuses to propose templates with adjacent slots unless both are fixed-width types.

### 8.4 Lineage span computation
```text
offset = 0; spans = {}
for token in template:
    if token.lit: offset += len(token.lit)
    else:
        v = vars[next]
        spans[token.slot] = (offset, offset + len(v))
        offset += len(v)
```
The UI maps each OCSF field back to its slot and highlights `spans[slot]` in the reconstructed raw.

### 8.5 Merkle sealing and verification
```text
seal(batch):
    leaves = [h for (uid, h) in sorted(batch.leaves, by uid)]
    while len(leaves) > 1:
        if odd: leaves.append(leaves[-1])
        leaves = [sha256(0x01 || leaves[i] || leaves[i+1]) for i in pairs]
    root = leaves[0]      # leaf level uses sha256(0x00 || h) to separate leaf/node domains
    chained = sha256(prev_chained(batch.source, batch.partition) || root || batch.key)
    store(batch, root, chained)

verify(range):
    for batch in range:
        recompute every event hash from storage (reconstruct or verbatim)
        recompute root and chained root
        compare with stored values and signed anchors
```
Domain separation bytes (`0x00` for leaves, `0x01` for internal nodes) prevent second-preimage tricks between leaves and internal nodes.

### 8.6 Clustering quarantined events (Drain3)
- Drain is an online log-template mining algorithm that groups log lines into clusters using a fixed-depth parse tree over tokens. Aletheia uses the Drain3 Python implementation.
- **Pre-masking** improves clustering: IPs, numbers, hex strings and timestamps are masked before clustering so that lines differing only in these values fall into the same cluster.
- Typical settings: similarity threshold around 0.4, tree depth 4. These are tuned per deployment.
- Output: clusters with a token-level template such as `Built <*> TCP connection <*> for <*>`.

### 8.7 Deriving an exact template from a cluster
Drain templates are token-based and lose exact whitespace. Aletheia converts them to byte-exact templates:
1. For all sample lines in the cluster, compute the positions of the variable tokens reported by Drain.
2. Refine token boundaries at the character level: split variable tokens further where characters like `:`, `/`, `(`, `)`, `=` separate parts that are constant across samples (for example `outside:203.0.113.5/443` becomes literal `outside` or slot, `:`, slot, `/`, slot).
3. Take the literal segments between variables **from the sample bytes themselves**, including exact whitespace. A segment becomes a literal only if it is byte-identical in every sample; otherwise it becomes a slot.
4. Merge adjacent literals; ensure no two slots are adjacent (insert splitting only where a literal separator exists).
5. For structured formats (CEF, LEEF, key=value, CSV), skip Drain entirely: the structure itself defines the template (Section 9), making derivation deterministic.

### 8.8 Slot typing and mapping proposal
**Typing** uses all sample values of a slot:
| Evidence | Assigned type |
|---|---|
| All values parse as IPv4/IPv6 | `ip` |
| All integers in 0 to 65535, and the preceding literal ends in `/` or `:` after an IP, or key name contains `port` | `port` |
| All match a timestamp format | the matching timestamp type |
| Small fixed set of words (for example allow, accept, permit, deny, drop, block, reject) | `enum` |
| Six hex pairs | `mac` |
| Values contain spaces and are followed by a literal | `text` |
| Otherwise | `word` |

**Mapping proposal** combines slot type with context:
- Key names in KV formats (`srcip`, `src`, `sip`, `dstip`, `dst`, `dpt`, `act`, `action`, `user`, `suser`, `proto`) map through a curated synonym table to OCSF paths.
- Literal context in free text (`from`, `to`, `for`, `src`, `dst`, `user`, `username`) informs direction and role.
- Protocol and action enums map to OCSF enum ids.
- Each proposal carries a confidence score and the evidence used, shown to the reviewer.

**Optional AI assistant:** the Studio can ask an AI model for a second opinion on mappings and slot splits. The model is never bundled; the operator chooses a cloud vendor with their own API key or a self-hosted endpoint they run. Full specification in Section 8.12. The heuristics above always run first and work with no AI configured.

### 8.9 The reconstruction gate
A proposed pack version is rejected unless all of these pass:
1. **Byte-exact reconstruction:** 100% of cluster samples match the template and reconstruct identically (hash equality).
2. **Type validation:** every slot value in every sample passes its type validation.
3. **Golden tests:** all existing tests of the pack still pass (no regression).
4. **No adjacent ambiguous slots.**
5. **Coverage report:** share of quarantined lines of this source that the new template now matches.

The gate proves the template is structurally correct for the data. It does not prove that mappings are semantically correct; that is what replay diff and human review are for.

### 8.10 Replay diff (blast radius)
```text
events = last N events of the source (or a time range), including raw_only ones
for e in events:
    raw = reconstruct_or_verbatim(e)
    old = engine(pack_version_current).process(raw)
    new = engine(pack_version_proposed).process(raw)
    diff(old, new) field by field
report:
    events newly matched (raw_only -> full/partial)
    events that change template
    per OCSF field: count changed, example before/after
    events that would get worse (full -> partial or raw_only)   <- highlighted as blocking
```
The reviewer sees exactly what the change will do before it goes live. The SHA-256 of the report is stored with the approval in the audit log.

### 8.11 Backfill after approval
Quarantined `raw_only` events of the affected source can be re-processed with the new pack. They are rewritten as `template` mode with a higher `pack_version` (replacing the verbatim row via `ReplacingMergeTree`). Their `raw_sha256` and Merkle membership never change, because those are computed from raw bytes, which are identical.


### 8.12 Pluggable AI assistant (bring your own model)

#### 8.12.1 Principle
The Aletheia image contains **no model weights and no inference runtime**. AI is an optional, external helper for onboarding only. This keeps the image small, keeps model choice with the operator, and keeps the core system fully functional without any AI.

Three operating modes:

| Mode | What the operator provides | Data leaves the machine? | Allowed in air-gap mode |
|---|---|---|---|
| **None** (default) | Nothing | No | Yes |
| **Cloud vendor** | An API key for OpenAI, Google Gemini, Groq, Anthropic, or any OpenAI-compatible vendor | Yes, masked samples only (Section 8.12.5) | No |
| **Self-hosted** | A URL of a model server they run: Ollama, llama.cpp server, vLLM, LM Studio, or any OpenAI-compatible server | Only to that server (usually the same host or LAN) | Yes, if the address is private |

#### 8.12.2 Supported providers
| `ALETHEIA_LLM_PROVIDER` | Protocol used | Default base URL | API key |
|---|---|---|---|
| `none` | none | none | no |
| `gemini` | Gemini native API (`generativelanguage.googleapis.com`) | `https://generativelanguage.googleapis.com/v1beta` | yes |
| `local` | OpenAI-compatible (`/v1`) | `http://localhost:11434/v1` (Ollama default) | no |

`local` covers Ollama, vLLM, the llama.cpp server, LM Studio and any other server that exposes an OpenAI-compatible chat completions API. `ollama` is accepted as a legacy alias for `local`. Default URLs can always be overridden with `ALETHEIA_LLM_BASE_URL`. The **model name is always the operator's choice** (`ALETHEIA_LLM_MODEL`); Aletheia does not hard-code vendor model names because they change often. The README lists the models tested at release time. The default model is `gemini-3.5-flash-lite`.

#### 8.12.3 Adapter design
- One interface in the Studio: `complete_json(system_prompt, user_prompt, json_schema) -> dict`.
- Two implementations cover every provider:
  - **GeminiProvider**: Gemini's native `generateContent` API with `response_schema` for structured output.
  - **OpenAICompatibleProvider**: Ollama, vLLM, llama.cpp, LM Studio and similar.
- Both use plain HTTPS calls (`httpx`), not vendor SDKs, so the image carries no vendor dependencies and adding a vendor is configuration, not code.
- Adding a new protocol means writing one small adapter class that implements the same interface.

#### 8.12.4 Structured, validated output
1. Aletheia asks for JSON output. It uses the strongest mode the endpoint supports: JSON schema mode, then plain JSON mode, then instructions in the prompt only.
2. The response is parsed and validated against a JSON schema whose OCSF target paths are an **enumerated list of allowed paths** for the chosen class. Any other path is invalid.
3. On validation failure, one retry is made with the validation errors included in the prompt.
4. If it still fails, the AI suggestion is discarded and the Studio shows "AI suggestion unavailable". The heuristic proposal is unaffected.
5. A valid suggestion is only a **proposal**. It goes through the reconstruction gate (Section 8.9), replay diff (Section 8.10) and human approval, exactly like a heuristic proposal. AI can never approve.

What the AI is asked: given the template (literals and typed slots) and a few sample values per slot, propose the OCSF class, the slot-to-path mapping, enum value mappings, and whether any slot should be split. It is one request per **cluster** during onboarding, never per event.

#### 8.12.5 Data minimization and masking
Log samples can contain sensitive data (internal IPs, usernames, hostnames). Controlled by `ALETHEIA_LLM_SEND_SAMPLES`:

| Value | Behaviour | Allowed for |
|---|---|---|
| `masked` (default for cloud) | Sample values are replaced by consistent, format-preserving placeholders: IPv4 addresses become documentation-range addresses (`10.0.0.5` to `192.0.2.1`, same input always the same placeholder), IPv6 likewise within `2001:db8::/32`, usernames `user_1`, hostnames `host_1`, MACs a fixed placeholder range. Ports, protocol words, action words and numbers of non-sensitive types are kept because they carry meaning. | All providers |
| `none` | Only the template and slot types are sent, no sample values | All providers |
| `raw` | Real sample values are sent | **Self-hosted providers only**; rejected for cloud providers |

Format preservation matters: a masked IPv4 is still an IPv4, so the model can still infer that a slot holds an address.

#### 8.12.6 Air-gap guard
- `ALETHEIA_AIRGAP=true` makes the Studio refuse any cloud provider at startup and in the UI.
- In air-gap mode, a self-hosted base URL must resolve to a loopback, private (RFC 1918), link-local or `host.docker.internal` address.
- When a cloud provider is active, the UI shows a persistent banner: "Cloud AI enabled: masked samples are sent to <provider>."
- This guard is a safety net; the real air-gap is enforced by the network.

#### 8.12.7 Keys and secrets
- The API key can be supplied in three ways, in order of preference:
  1. A mounted file: `-v ./llm.key:/run/secrets/llm_key:ro` with `ALETHEIA_LLM_API_KEY_FILE=/run/secrets/llm_key`.
  2. An env file: `docker run --env-file aletheia.env ...` (keeps the key out of shell history).
  3. The Studio **Settings** page, where it is stored encrypted (AES-GCM, key derived from `ALETHEIA_SECRET`) in PostgreSQL.
- Passing the key with `-e` works but makes it visible in `docker inspect`; the README says so.
- Keys are never logged, never returned by the API (the UI shows only the last four characters), never written into parser packs and never included in exports.

#### 8.12.8 Settings page and connection test
The Studio Settings page shows the active provider, base URL, model and masking mode, and has a **Test connection** button that:
- sends a tiny structured request and checks the reply parses,
- detects which JSON output mode the endpoint supports,
- reports latency,
- lists available models where the endpoint supports it (`GET /models`; for Ollama, the installed models).

Settings changed in the UI take effect immediately; environment variables provide the startup defaults.

#### 8.12.9 Limits, cost and provenance
- Timeout per request (default 120 s), bounded maximum output tokens (default 8192), at most one request per cluster plus one retry, and a per-hour request cap (default 60).
- A usage counter (requests, tokens where reported) is shown in Settings.
- Every proposal records its origin: `heuristic` or `ai:<provider>/<model>`. The audit log records which provider and model contributed to each approved pack version (never the key).
- **Lyra limits:** up to 5 tool-call steps per turn, 20 messages of history, 200 result rows, 30 rows sent to the model, 120-char cell truncation.

#### 8.12.10 Running a local model with Ollama (the operator's own machine)
**Option A: Ollama on the host.**
```bash
# on the host
ollama pull qwen2.5-coder:7b          # any instruction-following model works; this is an example

# Linux only: let containers reach Ollama (by default it listens on 127.0.0.1)
OLLAMA_HOST=0.0.0.0 ollama serve

# start Aletheia
docker run -d --name aletheia -p 8080:8080 -p 3000:3000 \
  -p 5514:5514/udp -p 5514:5514/tcp \
  --add-host=host.docker.internal:host-gateway \
  -e ALETHEIA_LLM_PROVIDER=ollama \
  -e ALETHEIA_LLM_MODEL=qwen2.5-coder:7b \
  docker.io/<namespace>/aletheia:1.0.0
```
On Docker Desktop (Windows, macOS) `host.docker.internal` works without `--add-host`. On Linux, `--add-host=host.docker.internal:host-gateway` is needed, and Ollama must listen on an address reachable from the Docker bridge; if it listens on `0.0.0.0`, restrict access with the host firewall.

**Option B: Ollama as a sibling container.**
```bash
docker network create aletheia-net
docker run -d --name ollama --network aletheia-net -v ollama:/root/.ollama ollama/ollama
docker exec ollama ollama pull qwen2.5-coder:7b
docker run -d --name aletheia --network aletheia-net \
  -p 8080:8080 -p 3000:3000 -p 5514:5514/udp -p 5514:5514/tcp \
  -e ALETHEIA_LLM_PROVIDER=ollama \
  -e ALETHEIA_LLM_BASE_URL=http://ollama:11434/v1 \
  -e ALETHEIA_LLM_MODEL=qwen2.5-coder:7b \
  docker.io/<namespace>/aletheia:1.0.0
```

**Air-gapped local model.** On a connected machine, `docker save ollama/ollama` and copy the pulled model files (the `ollama` volume or `~/.ollama/models`); load and restore them inside the air-gapped network, then use Option A or B with `ALETHEIA_AIRGAP=true`.

**Hardware.** A 7B to 8B model quantized to 4 bits runs on CPU and needs roughly 5 to 8 GB of extra RAM on the machine running Ollama. A GPU makes it faster but is not required, because onboarding requests are rare.

#### 8.12.11 Using a cloud vendor
```bash
# aletheia.env  (keep this file private)
ALETHEIA_LLM_PROVIDER=gemini
ALETHEIA_LLM_API_KEY=<your key>
ALETHEIA_LLM_MODEL=<model name from the vendor>

  -p 8080:8080 -p 3000:3000 -p 5514:5514/udp -p 5514:5514/tcp \
  docker.io/<namespace>/aletheia:1.0.0
```

#### 8.12.12 Why this design
| Alternative | Problem it has | How the pluggable design avoids it |
|---|---|---|
| Bundle a model in the image | Multi-GB image; one fixed model; slower pulls for evaluators | Image carries no weights |
| Cloud AI only | Breaks air-gap; sends data out | Self-hosted and none modes; air-gap guard; masking |
| Local AI only | Forces every evaluator to install and run a model | Cloud key or none also work |
| AI required for onboarding | System fails when AI is unavailable or wrong | Heuristics always run; AI output is gated and reviewed |

## 9. Format handling, source by source

### 9.1 Syslog RFC 3164
```
<166>Sep 19 14:31:02 fw01 %ASA-6-302013: Built outbound TCP connection ...
```
- PRI = facility * 8 + severity; `166 = 20 * 8 + 6` (facility local4, severity informational).
- Envelope template: `<` pri `>` ts ` ` host ` ` body. Variants exist without host, with a tag, or with nonstandard timestamps.
- No year, no timezone: handled as in Section 6.7.

### 9.2 Syslog RFC 5424
```
<165>1 2026-09-19T14:31:02.123+05:30 edge-rtr01 sshd 812 ID47 [meta sequenceId="29"] message text
```
- Fields: PRI, VERSION, TIMESTAMP, HOSTNAME, APP-NAME, PROCID, MSGID, STRUCTURED-DATA, MSG. Absent fields are `-`.
- STRUCTURED-DATA is captured as a slot and additionally parsed into `unmapped.sd` key/values.

### 9.3 CEF
```
CEF:0|VendorX|NGFW|4.2|1001|Connection allowed|3|src=10.0.0.5 spt=52144 dst=203.0.113.5 dpt=443 proto=TCP act=allow
```
- Header: `CEF:Version|Device Vendor|Device Product|Device Version|Signature ID|Name|Severity|Extension`.
- Escaping: in the header, `\|` and `\\`; in extension values, `\=`, `\\`, and `\n`/`\r` for newlines.
- Extension is `key=value` pairs separated by spaces, where a value may contain spaces and extends until the next ` key=`.
- **Structural templating:** the template is derived from the header plus the ordered key list: literals `" src="`, `" spt="` and so on, with slots for values. Key order becomes part of the template identity. If a device changes key order, a new template is generated automatically and deterministically, no clustering needed.
- Common CEF keys map through a fixed table: `src`, `dst`, `spt`, `dpt`, `proto`, `act`, `suser`, `duser`, `request`, `rt` (receipt time).

### 9.4 LEEF
```
LEEF:2.0|VendorY|WAF|3.1|BLOCK|^|src=10.0.0.5^dst=203.0.113.9^usrName=alice^action=block
```
- Header: `LEEF:Version|Vendor|Product|Version|EventID|` and, in LEEF 2.0, an optional delimiter character field. Default attribute delimiter is tab.
- Structural templating exactly like CEF, using the declared delimiter.

### 9.5 Key=value (for example FortiGate)
```
date=2026-09-19 time=14:31:02 devname="FGT-EDGE" logid="0000000013" type="traffic" subtype="forward" level="notice" srcip=10.0.0.5 srcport=52144 srcintf="port2" dstip=203.0.113.5 dstport=443 dstintf="port1" proto=6 action="accept" policyid=12 sentbyte=1324 rcvdbyte=5120
```
- Values may be quoted. The quote characters are literals in the template, so reconstruction stays exact.
- Discriminator: `logid` plus `type/subtype`.
- `proto=6` is an IANA protocol number (6 = TCP), mapped to `connection_info.protocol_num` and `protocol_name`.

### 9.6 CSV inside syslog (pfSense / OPNsense `filterlog`)
```
<134>Sep 19 14:31:02 filterlog[1234]: 5,,,1000000103,em0,match,block,in,4,0x0,,64,0,0,DF,6,tcp,60,198.51.100.9,10.0.0.5,51514,22,0,S,1234567890,,64240,,mss;sackOK;TS;nop;wscale
```
- The body is a comma-separated record whose field positions depend on IP version and protocol (the documented `filterlog` layout: rule number, sub-rule, anchor, tracker, interface, reason, action, direction, IP version, then IP-specific and protocol-specific fields).
- Templates are per `(ip_version, protocol)` variant; commas are literals, fields are slots; empty fields are empty-string slots.

### 9.7 JSON (for example Suricata EVE)
```json
{"timestamp":"2026-09-19T14:31:02.123456+0530","flow_id":123,"in_iface":"eth0","event_type":"alert","src_ip":"198.51.100.9","src_port":51514,"dest_ip":"10.0.0.5","dest_port":22,"proto":"TCP","alert":{"action":"allowed","signature_id":2001219,"signature":"ET SCAN Potential SSH Scan","category":"Attempted Information Leak","severity":2}}
```
- JSON is parsed with a streaming parser and mapped by **key path** (`alert.signature` to `finding_info.title`, and so on).
- **Storage mode is verbatim** for JSON by default, because byte-exact templating of arbitrary JSON (variable key order, whitespace, escapes, nesting) is fragile. The data is still fully parsed and normalized; only the storage representation differs. ZSTD compresses repetitive JSON well.
- `parse_status` reflects parsing and mapping quality; `storage_mode` reflects how bytes are kept. These are independent.

### 9.8 Space-delimited (Squid native access.log)
```
1789828262.123    245 10.0.0.5 TCP_TUNNEL/200 5120 CONNECT example.com:443 - HIER_DIRECT/93.184.216.34 -
```
- Fields: timestamp with milliseconds, elapsed ms, client IP, result code/HTTP status, bytes, method, URL, user, hierarchy/peer, content type.
- The variable run of spaces after the timestamp is captured as a whitespace slot (type `ws`), so alignment padding reconstructs exactly.

### 9.9 Free text (Cisco ASA, OpenVPN)
```
<29>Sep 19 14:31:02 vpn01 openvpn[812]: 198.51.100.20:50112 TLS: Username/Password authentication succeeded for username 'analyst1'
```
- Handled by curated or Studio-derived templates keyed by discriminators (ASA message ID; OpenVPN phrase prefixes).
- ASA has hundreds of message IDs; the prototype covers the connection build/teardown and deny families, and the Studio demonstrates onboarding of further IDs.

### 9.10 XML
Mentioned in the PS background but uncommon for perimeter devices. Handled like JSON: streaming parse, path-based mapping, verbatim storage mode.

## 10. OCSF normalization

### 10.1 Why OCSF
OCSF is an open, vendor-neutral schema for security events, developed by a broad group of security vendors and adopted by platforms such as Amazon Security Lake. Using it means:
- Output is immediately understood by tools that already speak OCSF.
- The schema is documented, versioned and maintained publicly.
- Inventing a custom schema would contradict "vendor-agnostic" and would need its own documentation and adoption.

The OCSF version is **pinned** for the whole deployment and recorded in `metadata.version`.

### 10.2 Classes used for perimeter devices
| Class | class_uid | Used for |
|---|---|---|
| Network Activity | 4001 | Firewall connection build/teardown/allow/deny, router ACL hits, flow records |
| HTTP Activity | 4002 | Proxy and WAF requests |
| DNS Activity | 4003 | DNS logs from firewalls/resolvers at the edge |
| Authentication | 3002 | VPN logins, admin logins to devices |
| Detection Finding | 2004 | IDS/IPS alerts, WAF rule hits reported as detections |

Field names in examples follow OCSF 1.x conventions (`src_endpoint`, `dst_endpoint`, `connection_info`, `traffic`, `metadata`, `unmapped`). Exact availability of some attributes (for example `action_id` and `disposition_id` on Network Activity) depends on the pinned version and profiles; packs are validated against the pinned schema.

### 10.3 Example mappings
| Source | Raw field | OCSF path |
|---|---|---|
| ASA 302013 | initiator IP/port (depends on direction) | `src_endpoint.ip`, `src_endpoint.port` |
| ASA 302013 | connection id | `connection_info.uid` |
| ASA 106023 (deny) | `Deny tcp src ... dst ... by access-group "X"` | Network Activity, activity Refuse; ACL name to `unmapped.acl` |
| FortiGate | `srcip`, `srcport`, `dstip`, `dstport` | `src_endpoint.*`, `dst_endpoint.*` |
| FortiGate | `sentbyte`, `rcvdbyte` | `traffic.bytes_out`, `traffic.bytes_in` |
| FortiGate | `action="accept"` | action allowed |
| pfSense filterlog | `block`, `in`, `em0` | action denied, direction inbound, interface name |
| Suricata alert | `alert.signature`, `alert.signature_id`, `alert.severity` | Detection Finding `finding_info.title`, `finding_info.uid`, severity mapping |
| Squid | method, URL, status | HTTP Activity `http_request.http_method`, `http_request.url`, `http_response.code` |
| OpenVPN | `authentication succeeded for username 'x'` | Authentication, `user.name`, status success |

### 10.4 Enum normalization
Action words vary by vendor (`accept`, `allow`, `permit`, `pass` versus `deny`, `drop`, `block`, `reject`). A shared table maps them to a canonical allowed/denied value. The original word always remains in `vars` and is visible in lineage.

## 11. Output sinks, including Loki

### 11.1 ClickHouse (primary)
Batch inserts from workers (thousands of rows per insert) through the native protocol client. Grafana reads it for dashboards; analysts query it with SQL.

### 11.2 Parquet data lake (MinIO)
Periodic export using ClickHouse's `s3` table function writing Parquet to MinIO, partitioned by `class_uid`, date and source. Typed columns make it ready for Python/Spark/DuckDB ML workflows (requirement h).

### 11.3 Grafana Loki
- Vector consumes the `normalized` topic and pushes to Loki (Vector's `loki` sink), or workers push directly to Loki's HTTP push API.
- **Labels must be low-cardinality**, because Loki indexes only labels and each unique label combination creates a stream. Allowed labels: `vendor`, `product`, `device`/`source_id`, `ocsf_class`, `parse_status`.
- **Never labels:** IP addresses, ports, usernames, `event_uid`. These would create millions of streams.
- `event_uid` and `template_id` go into **structured metadata** (supported in Loki 3.x), so a log line in Grafana can be linked back to the full record and lineage view.
- The log line itself is the normalized OCSF JSON; LogQL's `| json` parser can filter on its fields at query time.
- **Why Loki is a sink and not the main store:** field-level aggregations across billions of events (for example top talkers by `src_ip`) require parsing lines at query time in Loki, which is slow at this scale. ClickHouse stores fields as columns and handles these queries efficiently. Loki is valuable for live tailing and for teams already using Grafana.

### 11.4 Kafka consumers
Any external system can subscribe to the `normalized` topic. This is the simplest integration path for custom SIEMs and stream analytics.

### 11.5 Splunk HTTP Event Collector
POST JSON events to `/services/collector/event` with a token; `sourcetype` set per OCSF class.

### 11.6 CEF re-emit over syslog
For SIEMs that only ingest CEF, a mapping table converts OCSF fields back to CEF keys (`src`, `dst`, `spt`, `dpt`, `act`, and so on) and sends over syslog TCP/TLS. The result is a uniform CEF feed from heterogeneous sources.

### 11.7 Optional raw_data on export
Any sink can request `raw_data` to be filled by reconstruction at export time, so downstream tools can have the original without Aletheia storing it twice.

## 12. Scalability, delivery semantics and performance

### 12.1 Horizontal scaling
- Workers are **stateless** apart from in-memory Merkle leaf buffers that are flushed to the sealer, and the compiled matcher index that is rebuilt from the registry.
- Scaling out means adding workers to the consumer group; Redpanda rebalances partitions.
- Throughput scales with partitions and workers until ClickHouse insert capacity is reached; ClickHouse itself scales with shards.

### 12.2 Per-event cost
- One SHA-256 over roughly 300 bytes.
- One hash map lookup for candidates, usually one anchored RE2 match.
- One reconstruction (memory copy) and one more SHA-256.
- Type coercion and mapping.
All are CPU-bound and allocation-light in Go. Actual throughput is measured, not assumed (Section 17).

### 12.3 Batching and backpressure
- ClickHouse inserts are batched by size or time (for example 10,000 rows or 1 second).
- Offsets are committed only after a successful insert.
- If ClickHouse is slow or down, workers stop committing and consumption slows; Redpanda retains data; Vector's disk buffers absorb collector-side pressure. Consumer lag is the key alert metric.

### 12.4 Delivery semantics
- **At-least-once** delivery from the bus.
- **Idempotent writes** through deterministic `event_uid` and `ReplacingMergeTree`.
- Net effect: no loss, and duplicates collapse.
- Merkle leaves are deduplicated by `event_uid` before sealing.

### 12.5 Reprocessing
Because every event can be reconstructed exactly, historical data can be re-normalized with a new pack version (for example after fixing a mapping) without re-collecting logs. Reprocessed rows carry the higher `pack_version`; integrity hashes and Merkle roots are unaffected.

### 12.6 Template count management
Structural formats with variable key order can create many templates. The registry tracks template counts per source and alerts on explosions; very high-variety sources fall back to verbatim storage with full parsing, keeping correctness while giving up some compression.

## 13. Distribution as Docker images, deployment and air-gapped operation

Aletheia is delivered to evaluators as a **Docker image pushed to a public container registry** (Docker Hub). The evaluator pulls one image and starts it with one command. The same source code also builds a multi-image production deployment.

### 13.1 Two deployment modes

| Mode | Artifact | Purpose | Scaling |
|---|---|---|---|
| **Evaluation (all-in-one)** | One image: `docker.io/<namespace>/aletheia:<version>` | Evaluators, demos, air-gapped trials on a single machine | Single host; worker count configurable inside the container |
| **Production (multi-image)** | Component images: `aletheia-worker`, `aletheia-sealer`, `aletheia-studio`, `aletheia-ui`, plus upstream images (Vector, Redpanda, ClickHouse, PostgreSQL, MinIO, Loki, Grafana, Prometheus), orchestrated by Docker Compose or Helm | Real deployments | Horizontal: many workers, multi-node bus and ClickHouse |

Both modes are built from the same repository, run the same engine binary and load the same parser packs. The all-in-one image is a packaging choice for convenient evaluation, not a different product.

### 13.2 What the all-in-one image contains

| Layer | Components inside the image |
|---|---|
| Collection | Vector, listening on syslog UDP/TCP 5514 and TLS 6514, plus internal inputs for the demo replayers |
| Bus | Redpanda, single node in development-container mode |
| Aletheia services | Worker(s), Merkle sealer, parser registry API, Onboarding Studio, UI (including the Demo Console), `aletheia` CLI |
| Storage | ClickHouse, PostgreSQL, MinIO |
| Views and monitoring | Grafana (pre-provisioned dashboards and data sources), Loki, Prometheus |
| Demo content | Parser packs with golden tests, recorded log corpora, a packet capture for live Suricata replay, the ASA drift variant, the scenario engine behind the Demo Console |

**Process supervision.** A container normally runs one process. The all-in-one image uses **s6-overlay** as PID 1, which:
- starts services in dependency order,
- forwards signals so `docker stop` shuts every service down cleanly,
- restarts a crashed service automatically,
- runs one-shot initialization jobs before dependent services start.

**Startup order.**
1. PostgreSQL, ClickHouse, MinIO, Redpanda.
2. Init jobs: create topics, apply ClickHouse and PostgreSQL schemas, create buckets, load the source registry and parser packs, generate a demo TLS certificate authority (generated at first start, never baked into the image).
3. Loki, Prometheus, Grafana.
4. Aletheia worker(s), sealer, registry API, Studio, UI.
5. Vector (last, so no log arrives before the pipeline can process it).

**Readiness.** `GET /healthz` on the UI port returns ready only when every service is healthy. Until then the UI shows a startup page listing each service and its state. A Docker `HEALTHCHECK` uses the same endpoint, so `docker ps` shows `healthy` when the stack is ready.

**State.** All data lives under `/data`. Without a mounted volume, every `docker run` starts a fresh, identical demo, which is what evaluators usually want. With `-v aletheia-data:/data`, state persists across restarts.

**What is deliberately left out.**
- **No AI model weights and no inference runtime.** The AI assistant is external by design (Section 8.12): the operator either supplies a cloud vendor API key (OpenAI, Gemini, Groq, Anthropic or any OpenAI-compatible vendor) or points Aletheia at a model server they run themselves (for example Ollama). With nothing configured, the Studio runs on heuristics alone. There is only one image tag per release.
- No secrets, tokens or production credentials. Demo credentials are documented and can be overridden with environment variables.

**Build properties.**
- **Multi-architecture:** built with `docker buildx` for `linux/amd64` and `linux/arm64`, so it runs on Intel/AMD machines and on Apple Silicon Macs. Every bundled component is available for both architectures.
- **Multi-stage build:** Go and React are compiled in builder stages; only binaries and static files enter the final image.
- **Telemetry disabled** in every component at build time (Section 13.6).
- **Pinned upstream versions** of every component, recorded in the README.
- **Published digest:** the README gives the image digest (`sha256:...`) so evaluators can run exactly the image that was tested, and the SHA-256 of the saved tarball for air-gapped transfer.
- **Image size** is several GB because it bundles databases and dashboards; the exact size is measured and stated in the README.

**Requirements.** Docker Engine or Docker Desktop; at least 4 CPU cores, 8 GB RAM allocated to Docker (Docker Desktop's default allocation may need to be raised) and 10 GB free disk.

### 13.4 Air-gapped installation

The image is pulled once on a connected machine and carried into the air-gapped network as a file.

```bash
# connected machine
docker pull docker.io/<namespace>/aletheia:1.0.0
docker save -o aletheia-1.0.0.tar docker.io/<namespace>/aletheia:1.0.0
sha256sum aletheia-1.0.0.tar          # compare with the value published in the README

# transfer through the organization's approved media process

# air-gapped machine
sha256sum aletheia-1.0.0.tar
docker load -i aletheia-1.0.0.tar
docker run -d --name aletheia -p 8080:8080 -p 3000:3000 \
  -p 5514:5514/udp -p 5514:5514/tcp docker.io/<namespace>/aletheia:1.0.0
```
- Nothing is downloaded at start or at run time: no packages, no models, no fonts, no map tiles, no update checks.
- Start with `-e ALETHEIA_AIRGAP=true`. The AI assistant is then either `none` or a self-hosted model carried into the network the same way (Section 8.12.10).
- Organizations with an internal registry (for example Harbor) inside the air-gapped network can `docker load` once and push the image there.
- For the production mode, all component images are saved into one tarball the same way (`docker save` accepts several images).

**Proving the air-gap claim.** Pull the image, then disconnect the machine from all networks (or block all egress on the host firewall), start the container and run every Demo Console scenario. All must pass. A container-only test with `--network none` is not suitable because it also blocks the published ports the evaluator needs for the UI.

### 13.5 Production deployment
- Docker Compose file (and optional Helm chart) with one service per component.
- Workers scale by replica count; Redpanda and ClickHouse are deployed as multi-node clusters.
- Same environment variables and parser pack format as the evaluation image.

### 13.6 No outbound calls
- Disable telemetry and update checks in every component (Grafana analytics and update checks, Redpanda usage reporting, and similar settings).
- The UI bundles all fonts, icons and JavaScript; it loads nothing from the internet.
- The only outbound call Aletheia can ever make is to an AI provider that the operator explicitly configures. With `none` or a self-hosted endpoint on the local network, nothing leaves the network; `ALETHEIA_AIRGAP=true` enforces this (Section 8.12.6).
- Time synchronisation uses the site's internal NTP source; correct clocks matter for receive timestamps and Merkle batch minutes.

### 13.7 Certificates
TLS for syslog, the bus and the UI uses certificates from the organization's internal certificate authority. The evaluation image generates a self-signed demo CA at first start and prints its fingerprint in the container logs; production deployments mount the organization's certificates.

### 13.8 Resource profile
- **Evaluation image:** 4 or more cores, 8 GB RAM, 10 GB disk for the default demo; more cores give higher benchmark numbers.
- **Optional self-hosted model:** runs outside the image on the operator's hardware; a 4-bit 7B to 8B model needs roughly 5 to 8 GB of additional RAM.
- **Production:** bus, workers and ClickHouse on separate nodes, sized from measured per-core throughput (Section 17).

## 14. Security of the framework itself

| Concern | Control |
|---|---|
| Log transport interception | Syslog over TLS (RFC 5425); mutual TLS where devices support it |
| Spoofed senders | Source resolution by peer address and listener; unknown peers are tagged `unknown:<ip>` and never inherit another source's packs |
| Malicious log content causing slow regex | RE2 linear-time matching; no backtracking engine in the hot path |
| Oversized messages | Configurable maximum message size (for example 64 KiB); larger messages stored verbatim and flagged |
| Unauthorized parser changes | Role-based access in the Studio: viewer, onboarder, approver; optional two-person approval |
| Silent parser changes | Every approval stored in an append-only audit log with the replay diff hash |
| Evidence tampering | Per-event hashes, chained Merkle roots, signed daily anchors, verify tool |
| AI provider API keys | Mounted secret file, env file or encrypted storage; never logged, returned or exported (Section 8.12.7) |
| Sensitive data sent to a cloud AI vendor | Format-preserving masking by default; `raw` samples refused for cloud providers; air-gap mode refuses cloud providers; visible banner when cloud AI is active |
| Prompt injection through log content (a log line containing instructions aimed at the model) | AI output is constrained to a JSON schema with an allow-list of OCSF paths, must pass the reconstruction gate and replay diff, and needs human approval; AI can never approve or run on live events |
| AI unavailable or wrong | Heuristic proposals always exist; AI suggestions are optional and gated |
| Secrets | Tokens (for example Splunk HEC) supplied via container secrets, not in pack files |

## 15. Failure modes and how each is handled

| Failure | Behaviour | Data outcome |
|---|---|---|
| Unknown format (drift or new source) | Stored verbatim, `raw_only`, referenced to quarantine | No loss; onboarding path triggered |
| Template matches but a slot fails validation | `partial`; raw substrings kept in `vars`; failure noted | No loss; visible in dashboards |
| Reconstruction hash mismatch | Stored verbatim; `dlq` entry; metric incremented | No loss; engine defect surfaced |
| Worker crash | Uncommitted messages redelivered; same `event_uid` | No loss, duplicates collapse |
| ClickHouse unavailable | No offset commits; lag grows; Redpanda retains | No loss while within retention |
| Redpanda unavailable | Vector disk buffers | No loss while buffer capacity holds |
| Bad parser approved | Replay diff should have caught it; if not, fix pack and reprocess | Raw intact; corrected by reprocessing |
| Clock skew on a device | Event time wrong, receive time correct; both stored | Analysts can see both |
| Template explosion | Alert; fallback to verbatim for that source | No loss; less compression |
| UDP packet loss in network | Outside Aletheia's control; recommend TCP/TLS | Documented limitation |

## 17. Evaluation metrics and benchmark methodology

Every number presented must be measured with this methodology and recorded with machine specifications. No unmeasured figures.

| Metric | Method | Reported as |
|---|---|---|
| **Throughput** | Replay a mixed corpus from all sources at increasing rate until lag grows; measure sustained events/sec with 1, 2 and 4 workers | Events/sec per core; scaling chart; comparison to 11,574 eps (1B/day average) and about 35,000 eps (3x peak) |
| **Storage efficiency** | Load the same corpus into `events` and into `baseline_events` (raw + normalized JSON), both ZSTD; measure compressed bytes from ClickHouse `system.parts` | Ratio versus baseline, and separately versus ZSTD-compressed raw alone (the honest, harder comparison) |
| **Verified rate** | Share of events stored as verified templates, per source | Per-source table |
| **Zero loss** | Count of messages produced by the generator versus rows stored | Must be exactly equal |
| **Integrity** | Flip one byte in storage; run verify | Detection of the exact batch and event |
| **Onboarding effort** | Time from first sample of a new source to `full` events via the Studio, versus measured time to hand-write an equivalent grok/regex parser for the same source | Minutes versus minutes |
| **Drift detection latency** | Time from first changed-format line to quarantine alert | Seconds |
| **Replay diff speed** | Time to diff N events between two pack versions | Seconds per N |

**Why the storage comparison is reported two ways:** ClickHouse compresses raw text with ZSTD very effectively on its own. Comparing only against uncompressed raw would overstate the benefit. Aletheia reports against (1) the realistic baseline of raw plus normalized copies and (2) compressed raw alone.

| Source | Device type | Origin of logs | How logs reach Aletheia inside the evaluation image | Formats exercised |
|---|---|---|---|---|
| pfSense or OPNsense | Firewall | Captured from a real virtual machine during development | Recorded corpus, replayed | RFC 3164 syslog with `filterlog` CSV body |
| Suricata | IDS/IPS | Real Suricata | **Runs live inside the image** in offline mode against a bundled packet capture of self-generated traffic | EVE JSON, fast.log text |
| OpenVPN | VPN | Captured from a real instance | Recorded corpus, replayed | Syslog free text |
| Squid | Web proxy | Captured from a real instance | Recorded corpus, replayed | Native access.log |
| Cisco ASA | Firewall | Generated from published message documentation | Generator | RFC 3164 with free-text message IDs |
| FortiGate | Firewall | Generated from published log reference | Generator | Key=value |
| Generic CEF and LEEF emitters | Firewall/WAF | Generated | Generator | CEF, LEEF |
| Evaluator's own logs | Any | Whatever the evaluator sends | Syslog port 5514 | Any |

- **Replay with fresh timestamps.** The replayer rewrites timestamps to the current time so dashboards look live. The rewritten line is what Aletheia receives, so it is the raw event that gets hashed and preserved; this does not weaken any lossless claim.
- **Correlated traffic.** The generators use shared IP pools and a fixed seed, so the same attacker IP appears in firewall denies, IDS alerts and VPN failures. This makes cross-source correlation visible and makes every run identical.
- **Drift variant.** An ASA variant with an extra field inserted into a message simulates a firmware change on demand.
- **Packet capture for Suricata** is produced by the team from its own lab traffic, so it carries no third-party licensing or privacy issues.
- **Honest statement:** four sources come from real software (one live in the image, three recorded); vendor-proprietary formats are generated from published vendor documentation because proprietary devices are not available.

## 19. Technology stack and justifications

| Layer | Technology | Justification | Main alternative and why not |
|---|---|---|---|
| Collection | Vector | Rust performance, all needed transports and framings, disk buffers | Logstash: heavier JVM, slower; Fluent Bit: fine, but Vector's routing and Kafka integration fit better |

### 21.3 How the tamper action works
The **Tamper one stored byte** action changes one character inside one event's stored variables directly in ClickHouse (a synchronous `ALTER TABLE ... UPDATE` mutation), bypassing Aletheia entirely, exactly as an attacker with database access would. Verification then recomputes the hash of the reconstructed event, finds the mismatch, and the Merkle root of that batch no longer matches the sealed root. **Reset demo** restores the original value.

### 21.4 A note on the benchmark inside one container
Scenario 8 runs on whatever machine the evaluator uses, with all services sharing that machine. It demonstrates that throughput scales with workers, but absolute numbers are lower than a production deployment where the bus, workers and ClickHouse run on separate nodes. The reference numbers from the team's measured runs, with hardware specifications, are shown alongside.

## 23. Prior art and differentiation

### 23.1 Existing tools and ideas
| Tool / idea | What it does | What it lacks relative to Aletheia |
|---|---|---|
| Logstash with grok, Fluentd, Fluent Bit | Collection and regex-based parsing | Hand-written parsers; backtracking regex; raw kept as a separate copy; event-level links only |
| Vector (VRL) | Fast collection and transformation | Same parser-writing burden; no lineage, gate or integrity chain |
| Cribl Stream | Commercial pipeline with routing, reduction and packs | Proprietary; parsing still authored by people; no byte-exact lossless proof |
| Elastic Common Schema, Splunk CIM | Common field naming | Tied to their ecosystems; no preservation model |
| OCSF | Open, vendor-neutral schema | A schema, not a pipeline; Aletheia adopts it |
| Drain (log template mining) | Clusters logs into templates | Research algorithm for mining; Aletheia uses it only for onboarding |
| CLP (Compressed Log Processor, YScope) | Stores logs as templates plus variables for high compression and search | Focused on compression and search; no OCSF normalization, no chain of custody, no gated parser lifecycle. It is prior art for Aletheia's storage idea |
| "LLM parses each log" approaches | Model output per event | Too slow and costly at 10k+ events/sec, non-deterministic, unsuitable as evidence, hard to run offline at scale |

### 23.2 The generic baseline and why Aletheia is above it
A typical solution to this PS is: collector, format detection, a parser registry (possibly with an LLM that generates parsers), a common schema (often OCSF), raw logs in object storage linked by a trace ID, and analytics in ClickHouse or Elasticsearch.

| Aspect | Generic baseline | Aletheia |
|---|---|---|
| Losslessness | Raw copy exists; asserted | Every event reconstructed and hash-verified; verbatim fallback |
| Storage | Raw plus normalized (two copies) | One representation serves both |
| Traceability | Event ID link | Byte-level lineage for every field |
| Integrity | Per-event hash, which can be recomputed by an attacker | Merkle chain with signed anchors |
| Parser creation | Hand-written or LLM-generated, trusted after light testing | Derived from data; any suggestion must pass byte-exact gate and replay diff |
| Format drift | Parse failure or dead-letter queue | Detected, stored, quarantined, clustered, onboarded |
| AI in the hot path | Sometimes | Never |

### 23.3 Compliance relevance (verify exact wording before citing externally)
- CERT-In directions issued in April 2022 require organizations to maintain logs of ICT systems for a rolling period of 180 days within Indian jurisdiction. At billions of events per day, efficient lossless storage directly reduces the cost of meeting this.
- The Bharatiya Sakshya Adhiniyam, 2023 (which replaced the Indian Evidence Act) addresses admissibility of electronic records, including a certificate requirement under Section 63 that involves hash values. Verifiable per-event hashes and a tamper-evident chain support producing such evidence.

## 25. Limitations and honest scope

- **JSON and XML** are fully parsed and normalized but stored in verbatim mode by default; the compression advantage applies mainly to text, syslog, CEF, LEEF, KV and CSV formats.
- **Reconstruction proves no loss, not correct meaning.** A template can reconstruct perfectly while a mapping assigns a value to the wrong OCSF field. This is mitigated by golden tests, replay diff and human approval, not by hashing.
- **Proprietary vendor formats** in the prototype are generated from published documentation, not captured from real devices.
- **UDP syslog** can lose packets on the network before reaching Aletheia; TCP or TLS is recommended.
- **Merkle integrity** proves stored data has not changed since sealing; it cannot prove that a device sent truthful logs.
- **Template explosion** is possible for highly variable structured sources; the fallback is verbatim storage with full parsing.
- **OCSF attribute availability** varies by version and profile; packs are validated against the pinned version.
- **Throughput** figures are only those measured on the stated hardware; production capacity depends on cluster size.
- **The all-in-one evaluation image is a single-node packaging** for convenience. It proves function and shows scaling with workers on one machine; it is not how a billions-per-day deployment is run (that is the production multi-image mode).
- **Image size** is several GB because databases and dashboards are bundled; no model weights are included.
- **AI suggestion quality depends on the model the operator chooses.** Small local models may propose weaker mappings than large cloud models; this affects only proposals, which are gated and reviewed.
- **Cloud AI providers receive masked samples.** Masking reduces but does not remove all information (for example, message structure and port numbers are still sent). Organizations that allow no data egress should use `none` or a self-hosted model.
- **Recorded corpora** for pfSense, OpenVPN and Squid are replays of real captures, not live devices, inside the evaluation image.
- **Scope** is perimeter network devices as required by the current PS scope; the design generalizes to other sources through new packs.

## 26. Anticipated questions and answers

**Is this not just Logstash with ECS?**
Logstash parsing relies on hand-written grok patterns with a backtracking regex engine, keeps raw as a second copy, links only at event level, and has no drift detection or tamper evidence. Aletheia derives parsers from data, gates them, stores one verifiable representation and links every field to exact bytes.

**CLP already does template-based compression.**
Yes, CLP is prior art for the storage idea and is acknowledged. CLP does not normalize to a security schema, does not provide a chain of custody and does not manage a gated parser lifecycle. Aletheia combines these into one pipeline for security data.

**What if a parser is wrong?**
Structural errors are caught by the reconstruction gate and golden tests. Semantic errors are caught by the replay diff and human review. If an error still reaches production, raw bytes are intact and historical events can be reprocessed with a corrected pack.

**Can it handle billions of events per day?**
One billion per day is about 11,574 events per second on average. Workers are stateless and scale with bus partitions; ClickHouse scales with shards. The measured per-core throughput and scaling chart are in the benchmark results.

**Where is the AI?**
Deliberately outside the evidence path. The hot path is deterministic compiled code. During onboarding an optional AI assistant can suggest mappings, and every suggestion must pass the byte-exact gate, the replay diff and human review.

**Which AI does it use?**
Whichever the operator chooses: a cloud vendor with their own key (OpenAI, Gemini, Groq, Anthropic or any OpenAI-compatible vendor), a model they host themselves (for example Ollama), or none. The image ships no model, so it stays small and model choice is not locked in.

**Doesn't using a cloud AI vendor break the air-gap requirement?**
Yes, which is why it is optional and refused in air-gap mode. In an air-gapped network the assistant is either off or a self-hosted model inside the network. Even with a cloud vendor, only masked samples are sent, once per cluster during onboarding, never live events.

**Does a local model need a GPU?**
No. A 4-bit quantized 7B to 8B model runs on CPU through Ollama. Onboarding requests are rare, so latency is acceptable, and heuristics work with no model at all.

**Why OCSF instead of your own schema?**
Interoperability. OCSF is open, documented and supported by existing platforms. A custom schema would contradict the vendor-agnostic requirement.

**How do you handle JSON logs?**
They are parsed and normalized fully; storage mode is verbatim because byte-exact templating of arbitrary JSON is fragile. This is documented as a limitation.

**A hash stored next to data can be forged.**
Correct, which is why hashes are sealed into per-minute Merkle roots that are chained over time and anchored with a signature held outside the data store.

**Why both Loki and ClickHouse?**
Loki is for live operational viewing and integration with existing Grafana setups, using low-cardinality labels only. ClickHouse handles field-level analytics and ML exports at scale.

**Everything runs in one container. Is that scalable?**
The single image is for evaluation convenience. The same engine and packs run in the production mode, where workers are separate containers scaled by replica count and Redpanda and ClickHouse are clusters. Scenario 8 shows throughput increasing with workers even inside one container.

**How do we know the image matches the submitted code?**
The README lists the image digest and the source commit it was built from, and the CI workflow that builds and pushes the image on each release tag is in the repository. The image can also be rebuilt locally with `docker/build.sh`.

**How do we test it air-gapped if it comes from Docker Hub?**
Pull once on a connected machine, `docker save` to a file, verify the checksum, `docker load` on the disconnected machine. Nothing is downloaded after that.

**Is your data real?**
Four sources are real software producing real logs. Proprietary vendor formats are generated from published vendor documentation.

**What happens when a device firmware changes its format?**
New lines stop matching; they are stored verbatim immediately, a quarantine alert fires, the Studio proposes a template, and after gate, replay diff and approval the source is back to full normalization with no restart. Quarantined events are backfilled.
